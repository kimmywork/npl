### R23 目录句柄不校验类型

`find_directory`（`lib/npl/unix/native/unix.c`）只检查 `npl_is_pointer` 和
`address != NULL`。去掉全局链表后，任何非 NULL 的指针盒都会被当作
`NplDirHandle *`：

- 探针 23：`(read-directory (foreign-alloc 64))` 在 npli 与 nplc 上 SIGSEGV
  （`readdir(NULL)`），`guard` 无法捕获。
- 探针 23b：`close-directory` 同样段错误；若内存内容非零，则对任意地址
  `closedir` 后再 `free`，之后 `foreign-free` 该所有者就是二次释放。
- 反方向：目录句柄是普通指针盒，`pointer-ref-*` 可直接读写 `NplDirHandle`。

第一轮的链表方案顺带承担了类型校验，第二轮建议（本审查提出）漏掉了这一点。
修法（NPL 优先）：在 `unix.sld` 中用 `define-record-type` 包一层
`directory-object`，`read-directory`/`close-directory` 先检查谓词再把内部指针交给
C；指针盒不导出给用户。C 层保留 NULL 检查。

测试：对 `foreign-alloc` 指针、`null-pointer`、普通 record 调用
`read-directory`/`close-directory`，都报可捕获错误。

### R24 int64 检查与 fixnum 解码不一致

fixnum 是 62 位（`npl_fixnum_value` 为 `v >> 2`），范围
[-2^61, 2^61-1]。`require-time-second` 与 `require-offset` 放行到 2^63-1，
大于 2^61-1 的值是 bignum，C 侧仍直接 `npl_fixnum_value`，解码出的是指针位：

- 探针 24：`set-file-times` 2^62 秒，mtime 被设为 1102749628（npli）/
  1075030468（nplc），每次运行不同；-2^62 同样。
- 探针 24b：`(truncate-file f (expt 2 61))` 把 10 字节的文件截/扩到约 1 GiB
  的随机长度；随机值小于原长度时就是**数据丢失**。`truncate-file` 的
  `require-offset` 在第一轮就存在，R21 新增的秒数检查复制了同一缺口。
- `srfi-170` 新用例只测 2^63、-2^63-1、2^70，都在 NPL 层被拒，覆盖不到。

修法：C 侧改用已有的 `npl_ffi_to_int64(value, INT64_MIN, INT64_MAX, "time_t", who)`
（`runtime/ffi.c`，能解 bignum 并报错），`npl_unix_set_file_times`、
`npl_unix_truncate_file`、`npl_unix_truncate_port` 三处都改；NPL 层的范围检查
保留为前置诊断。测试补 2^61、2^62、-2^61-1。

附注：2^40 秒得到 9223372036 是 APFS 时间戳上限的截断，属宿主行为，不算缺陷。

### R25 `set-file-times` 哨兵冲突

NPL 用 `(cons -2 0)` 表示 `time/now`、`(cons -1 0)` 表示 `time/unchanged`；
C 以秒数 `== -2`/`== -1` 判断。合法的 time-utc 秒数 -1（1969-12-31 23:59:59）和
-2 现在通过了 `require-time-second`，探针 25：-2 秒被设为当前时间，-1 秒保持
原值不变（-3、0 正常）。该缺陷在第一轮代码已存在，但属于 R21 的同一参数路径。

修法：把模式与秒数分开传，例如 C 原语增加 `access_mode`/`modify_mode` 参数
（0 显式、1 now、2 omit），或改用 nsec 位传 `UTIME_NOW`/`UTIME_OMIT` 的独立编码；
测试补 -1、-2 秒往返。

### R26 导入冲突诊断缺来源

当前行为（同一绑定重复导入不冲突，`string-hash` 这类不同定义才冲突）符合
R7RS，R17 的语义问题已经解决。剩下的是诊断只有名字。

worklog 记录的失败尝试是给 binding 增加 origin 字段，影响了 npli 的
`expand-derived-syntax`。可以不改绑定结构，只在报错时反查：

- 值绑定的 payload 是 `library-prefix` + 名字（`_npl_lib_N_name`），而
  `library-record-load!` 已把每个已加载库的 `prefix` 存进
  `library-entry-info`。`library-import-binding` 报冲突时，遍历
  `LIBRARY-REGISTRY`，找 info 的 prefix 是 `existing` 与新 payload 前缀的条目，
  得到两个定义库的 key；找不到则是 `primitive`。前缀带结尾 `_`，`_npl_lib_1_`
  不会误配 `_npl_lib_10_`。
- 只在 `fatal` 之前执行，不进入正常导入路径，也不改变 `library-binding` 的形状，
  因此不会影响 npli 的派生语法展开。
- 宏冲突的 payload 是 cell，无法同样反查，可先只给出名字；值冲突是常见情况。
- 可顺带报告“正在加载哪个库”（`library-load` 中 state 为 1 的条目），区分程序
  导入冲突与库内部导入冲突。

测试：`imports/` 增加一个导入 `(srfi 13)` 与 `(srfi 125)` 的负例，期望诊断同时
包含 `string-hash`、`srfi/13`、`srfi/125`。

### R27 `(npl util)` 的公共冲突

`(npl util)` 位于 `lib/npl`，是公开库，导出 `string-prefix?`、`string-suffix?`、
`string-index`、`string-contains?` 等，与 `(npl string)`、`(srfi 13/130/140)`、
`(npl data collection)` 是不同定义：

- 探针 27：`(import (npl string) (npl util))` 报
  `conflicting imported binding: string-prefix?`。
- `(npl util) string-index` 是子串搜索（相当于 SRFI 13 的 `string-contains`），
  SRFI 13/130 的 `string-index` 取字符或谓词。同名不同义，正是用户提到的
  “有明显不同行为”的情形，而且是这次新引入的。
- `npli tools/export-origins.npl` 现为 71 个冲突名（worklog 记为 69），新增的是
  `string-contains?`、`read-text-file`；`string-prefix?` 等组也多了一个来源。
  `check-export-origins` 不在 `tools/run-tests.npl` 中调用，所以增长没有被拦住。
- 另外，`check-duplicate-definitions` 只查私有定义；把私有 helper 改成
  公开导出，就绕过了这一检查，代价是导出冲突增加。

建议：

1. 改为 `(npl internal util)`（不承诺为公共 API），或至少把 `string-index` 改名
   （如 `string-search`）；能直接复用 `(npl string)` 的就复用。
2. 把 export origin 检查接入门禁：现有 69 组有意重叠写成基线（名字 + 来源集合），
   出现新名字或已有名字的新来源时失败。

### R28 `read-text-file` 重复

`(npl test expect)` 与 `(npl test util)` 都导出自己定义的 `read-text-file`
（都是 `read-file` 的包装），探针 28 同时导入即报冲突。`expect.sld` 可改为
从 `(npl test util)` 导入并重新导出 `read-text-file`，这样两者是同一绑定
（`write-text-file` 与 `write-text` 也可合并）。

### R29 `(npl process) delete-directory` 错误类型

R17 统一绑定后，`(npl process) delete-directory` 的失败从 file 错误
（`delete-directory: cannot delete directory`）变为 posix 错误：探针 29 中
`file-error?` 为 `#f`，消息是 `No such file or directory`，不带操作名。仓库内
没有依赖旧行为的代码，但这是 `(npl process)` 对外可见的变化，文档未提。

- `npl_primitive_posix_error` 的 `who` 参数未使用；`unix_raise` 原来也如此。
  SRFI 170 不规定消息格式，可考虑把 `who` 放进消息，与其他原语错误一致。
- 建议在 `docs/posix.md`（或 process 文档）注明该过程抛 posix 错误，并在
  `srfi-170` 或 process 套件中断言 `(npl process)` 导入路径下 `posix-error?` 为真。

## 后续修复（2026-11-24）

- **R23**：`open-directory` 返回私有 record `directory-object`；
  `read-directory`/`close-directory` 先检查谓词，`foreign-alloc` 指针、
  `null-pointer`、普通值均报可捕获错误。探针 23、23b 在 npli/nplc 都不再崩溃。
- **R24**：`set-file-times` 秒数、`truncate-file` 长度在 C 侧用
  `npl_ffi_to_int64` 解码（先于 `unix_path` 分配）。2^62 秒被宿主截到
  APFS 上限，2^61 长度报 `File too large`；不再出现随机值。
- **R25**：`time/now`、`time/unchanged` 的哨兵改放在纳秒位（-1/-2）；
  -1、-2 秒往返正确。
- **R26**：冲突诊断为 `conflicting imported binding: NAME (from (LIB A) and
  (LIB B))`，必要时附 `while loading (LIB)`；仅在报错时由 payload 前缀反查
  `library-entry-info`，绑定结构不变。npli 与 nplc 均验证。
- **R27**：`(npl util)` 只保留 `path-join`、`path-directory`、
  `path-normalize`、`exact-natural?`；字符串函数改用 `(npl string)`，原
  子串搜索 `string-index` 的调用改为 `string-contains`。
- **R28**：`(npl test util)` 是唯一定义处，`(npl test expect)` 重新导出
  `read-text-file`；`imports/test-expect-and-util.npl` 入门禁。此前未检出的
  原因：重复定义检查只比较私有定义，而两份都是导出的；导出冲突报告不在门禁中。
- **R29**：文档注明 `delete-directory` 经两个库都抛 posix 错误；`srfi-170`
  断言 `(npl process)` 路径。`who` 参数仍未进入消息（SRFI 170 的
  `posix-error-message` 是 strerror 文本）。
- **R30**：R19 回退由 `(tools link-modes)` 用 `build/bin/nplc`
  （`--emit-qbe`、`NPL_CC=/usr/bin/false`）测试；`docs/testing.md` 改正；覆盖率只计测试代码。
