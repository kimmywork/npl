# NPL 0.1.0 State Review

Status: read-only review, 2026-11-12. Findings feed the 0.1.1 work on
`release/0.1.1`. This document records evidence, not a release verdict for
later versions.

## Object and question

Object: tag `v0.1.0` (HEAD `a9102af`, clean tree) after the language
milestone and the release commits.

Question: is 0.1.0 correct and complete for its stated language-stage claim,
and is it ready for external use as a 0.1.x release?

Criteria: the project's own claim in `docs/r7rs-conformance.md`, the gate in
`docs/testing.md`, `AGENTS.md` engineering rules, and the toolchain behavior
described in `docs/toolchain.md` and `docs/ffi.md`.

## Findings

### F1. Release hygiene is incomplete (release blocker)

There is no root `README`, no project `LICENSE` (only the vendored QBE
license), and no repository CI configuration. `VERSION` and
`project(npl VERSION ...)` are informational; `nplc --version` and
`npli --version` both fail as unknown options (status 2).

Impact: an external user has no entry point, no license, and no automated
verification; a 0.1.0 tag is not a usable external release artifact.

### F2. The gate depends on the caller's locale (reproducibility defect)

`tools/run_tests.sh` does not set a UTF-8 locale. On a host with `LANG=""`,
Guile prints non-ASCII characters as `\x...;` escapes, so the Guile surface
of `unicode-strings` and `unicode-char` differs from the expected UTF-8
output. The Linux gate script sets `LC_ALL=C.UTF-8`; the macOS path does not.

Reproduction:

```bash
tools/run_tests.sh --skip-current-fixed-point
# R7RS unicode-strings FAIL
# R7RS unicode-char FAIL
LC_ALL=C.UTF-8 tools/run_r7rs_fixture.sh tests/r7rs/fixtures/unicode-char
# PASS on native, repl, and guile
```

This is a harness defect, not a language or Guile correctness defect.

### F3. Compiler diagnostics leak emitted SSA (usability defect)

`src/compiler/driver.npl` relays the complete partial SSA file to standard
error when the child compiler fails. A backend arity error therefore prints
tens of thousands of SSA lines before the actual diagnostic:

```bash
printf '(import (scheme base) (scheme write))\n(define (f x) (car x x))\n(display (f (list 1)))\n' > /tmp/e2.scm
build/bin/nplc /tmp/e2.scm -o /tmp/e2
# stderr: 37,387 lines / 974,786 bytes, ending "nplc1: too many arguments expected=1"
```

Diagnostics still use the stale `nplc1:` prefix and usually have no source
location; the reader's paren check is the exception. `car` is not named in
the arity message. `docs/toolchain.md` promises that the diagnostic is
relayed, not the whole SSA stream.

### F4. Test-count documentation has drifted

`docs/testing.md` says 57 stages without the relay and 58 with it; the gate
in this review has 56 and would have 57. It also says 35 compiler suites and
45 contracts; `tools/check_full_compiler.sh` registers 30 `run_suite`
programs and 77 negative checks (plus inline SSA and C-extension probes).
`docs/toolchain.md` still lists a 2026-09-29 self-compilation figure of 338 G
instructions; the current recorded figure is 11.1 G.

Impact: the documents that define "what to run" no longer describe the gate
that exists.

### F5. Feature detection is narrower than the implementation

`features` returns only `(r7rs npl)`. NPL supports full Unicode, exact
ratios, exact complex numbers, exact closure of `+ - * expt`, IEEE inexact
numbers, bignums, and POSIX platforms, but does not advertise the
corresponding standard feature identifiers.

`cond-expand` also does not see installed `(srfi ...)` or user libraries:

```bash
build/bin/npli -e '(import (scheme base) (scheme write))
  (write (cond-expand ((library (srfi 125)) (quote yes)) (else (quote no))))
  (newline)'
# no
```

`library-feature-library?` checks only the `(scheme ...)` index or libraries
already in the registry, not whether the library file exists. Portable
`cond-expand` users therefore get false negatives for available libraries.

### F6. Uncaught-error behavior differs between the two execution paths

A native program with an uncaught error exits 1; npli exits 70. Both print
only `who: message` (native) or `error: ...` (npli), with no call stack and
no source location. R7RS leaves the exit status implementation-defined, but
the two paths should agree or the difference should be an explicit,
documented contract.

### F7. Build configuration advertises unsupported knobs

`NPL_TARGET` (described as `arm64|amd64|rv64`) and `NPL_BOOTSTRAP_STAGE` are
defined and printed by CMake but have no implementation. There is no
cross-compilation path and no Windows support; the supported platforms are
macOS arm64 and Linux (x86_64/aarch64).

### F8. Known language/consistency gaps remain

- Native and npli differ in operand evaluation order when an operand has a
  side effect visible to another; R7RS leaves the order unspecified, but the
  project's own rule is that the paths agree.
- `(sqrt -1.0-0.0i)` follows the IEEE signed-zero branch (`0.0-1.0i`), while
  chibi's test expects the other branch; the decision is still open.
- A literal number in call position, such as `(2 3)`, reports
  `control conversion: unsupported core form`, a compiler-internal message.
- `nplc` on a missing source file exits 1; `npli` exits 66.

None of these blocks the R7RS-small claim; they are consistency and
diagnostic quality gaps.

### F9. Performance gaps are known and bounded

Recorded measurements through 2026-11-06: native is ahead of Guile on
`fib`/`tak`/`loop`, level on `fact`/`vectors`/`closures`/`strings`, about 2x
on `lists`, and about 4x Racket on `callcc`; npli is about 2-3x the Guile
interpreter. A hello-world compile is about 1 s because the whole program and
its libraries are compiled together. The remaining lists cost is allocation
and GC; incremental stack scanning was explicitly deferred.

### F10. Ecosystem and language extensions remain deliberately out

SRFI 1/13/113 are absent; `syntax-case`, keyword/optional arguments, record
inheritance, an object system, and `pretty-print` are absent; FFI has no
callbacks, structs, arrays, or variadic functions; there are no threads; and
there is no separate compilation, package manager, `staticlib`, or `dylib`
output. These are product decisions, not regressions, but they bound what
0.1.x can be used for.

### F11. Unicode table generation is host-dependent

`tools/gen_unicode.py` uses the host Python's `unicodedata.unidata_version`
(15.1.0 here). A Python upgrade changes the generated tables; the commit
should pin the UCD version or record the prerequisite explicitly.

### F12. Original project positioning is not in the current docs

The historical README described NPL as a typed Scheme with neural-network
constructs; current 0.1.0 documentation claims only R7RS-small. If the typed
or NN direction is still active, it needs a new design and roadmap; if not,
the new README should state the current scope explicitly.

## Verdict

- Language-stage claim: **pass** on the evidence rechecked here, with the
  documented exceptions and the un-rerun relay/Linux/chibi checks noted.
- External 0.1.x release readiness: **conditional**. F1-F4 should be fixed
  before presenting 0.1.1 as a public release; F5-F7 are high-value polish;
  F8-F12 are roadmap items or explicitly accepted limits.

## Next actions

0.1.1 (this branch): a root README and a GitHub Pages README under `docs/`,
MIT LICENSE, Linux-only CI, `--version`, locale-stable gate, clean compiler
diagnostic channel and prefixes, feature identifiers plus `cond-expand`
library detection, and synchronized test/version documentation.

Later: source spans and stack traces, unified uncaught exit status, SRFI 1/13
/113 and package tooling, separate compilation, GC/compile-time work, and a
decision on the typed/NN direction.

## Resolution on the 0.1.1 branch

F1 (README, MIT license, Linux CI, `--version`), F2 (UTF-8 locale), F3
(diagnostics on standard error, no partial-SSA relay, `nplc:` prefix), F4
(document counts), and F5 (feature identifiers and `cond-expand` library
detection) are addressed on `release/0.1.1` (PR
[#1](https://github.com/kimmywork/npl/pull/1)). Source spans and stack traces
are still open; F6-F12 remain roadmap or accepted limits.

## Limitations

This review is a single-agent check. It did not rerun the strict seed relay,
the Linux container gate, or the external chibi suite; it did not audit the
runtime for memory-safety defects, review every semantic edge case, or
perform a legal review. The gate result is for this macOS host and is
reported with the locale caveat above.
