## 结论

1. R2、R5、R7、R9、R12 的修复干净；R8 的声明已全部删除。
2. R1、R4 的修复各自引入一个**内存安全**问题：控制块写入缺写屏障，
   存活分配会被判为已释放（R13）；目录句柄按 malloc 地址登记，地址复用后
   旧句柄能读写并关闭新目录（R15）。这正是第一轮对 R4 原方案指出的问题。
3. 控制块只保护了 `pointer-*` 访问，struct 参数进入 C 的路径没有检查，
   释放后的 struct 以 NULL 传入 C 并段错误（R14）。
4. R6、R10、R3 的修复带来兼容性回归或残留：`NPL_C_STRUCT_LAYOUTS` 会屏蔽
   核心缓存（R19）；stub 不再包含系统头后 typedef 名的 struct 不能编译（R18）；
   `set-file-times` 秒数和 `open-file` flags 未限定范围（R21）。
5. 新增的 link mode 与 `(npl unix)` 改动另有两处回归：`NPL_NATIVE_LINK`
   从不生效（R16）；同时导入 `(npl unix)` 和 `(npl process)` 报绑定冲突
   （R17）。

### R13 控制块缺写屏障

`runtime/ffi-memory.c` 的 `ffi_alloc_block` 先 `npl_pointer(memory)` 分配指针盒，
再 `ffi_new_block` 分配控制块，最后把控制块存进 `pointer->block`。`npl.h` 规定
只有“同一函数刚分配、且其后没有再分配”的对象可以省略写屏障；这里分配控制块
可能触发 minor GC，使指针盒晋升为老对象，随后年轻的控制块只被这个未登记的
老对象引用，下一次 minor GC 把它回收。

- `NPL_GC_VERIFY=1`：`old tag 24 holds young tag 26 without a barrier`
  （24 = `BOX_POINTER`，26 = `BOX_FFI_BLOCK`）。
- 不开校验：nursery 2048/4096/8192 下 2 万个保留分配中 91/39/28 个报
  `allocation was freed`；**默认 GC 参数**下 30 万个中 12 个。
- 反方向同样可能：被回收的控制块内存被复用后，如果 `live` 位置读到非零，
  已释放的视图被当作存活，R4 重现。
- 修法：先分配控制块再分配指针盒，或在存入后调用
  `npl_gc_write_barrier(pointer, block)`。
- 现有 `ffi-memory` 的 10^5 压力循环是分配后立即释放，覆盖不到；需要保留分配并
  配合小 nursery 与 `NPL_GC_VERIFY` 的用例。

### R14 释放后的 struct 传入 C

`npl_ffi_struct_pointer` 新增了 `c-type` 比对，但最后直接返回
`npl_pointer_address(record->data[1])`。`free-c-struct` 后所有者地址为 NULL，
生成的 stub 把 NULL 交给 C。探针 14 调用 `gmtime_r`，nplc 在 “after free” 之后
SIGSEGV，`guard` 无法捕获。

建议在这里同样检查：地址非 NULL、控制块存活、`foreign-size` 不小于描述符的
`size`（防止以较短的视图构造的 record）。`(npl time)` 的 C 原语也经过这里。

### R15 目录句柄地址复用

R1 的修复把 `NplDirHandle` 放进全局链表，`find_directory` 按 malloc 地址查找；
`close-directory` 释放该节点。之后的 `open-directory` 可能复用同一地址，旧句柄
就重新“有效”。探针 15：关闭 `/usr` 的句柄后读到 `/etc` 的条目；对旧句柄
`close-directory` 把新打开的目录关掉，新句柄随后报 `directory is closed`。

更简单的修法：句柄本身就是每次 `open-directory` 新建的指针盒，关闭时把它的
`address` 置 NULL，读和关闭时检查 NULL。不需要全局链表，`threads.md` T1 中为
链表加锁的事项也随之取消。

### R16 `NPL_NATIVE_LINK` 不生效

`driver-config` 把 `DRIVER-NATIVE` 槽初始化为 `"static"`，
`driver-native-mode` 只在该槽为 `#f` 时读环境变量，所以环境变量永远不被读取。
`NPL_NATIVE_LINK=shared` 得到 477424 字节的静态产物，`--native=shared` 得到
347296 字节、依赖 `npl_runtime` 的动态产物。`docs/toolchain.md` 和 `--help`
都把该变量写为可用。环境变量的取值也没有像 `--native=` 那样校验
（`dynamic` 被静默当作 static）。`(tools link-modes)` 只用 `--native=`，未覆盖。

### R17 `delete-directory` 绑定冲突

`32cfa51` 中 `(npl unix)` 以 `(only (npl process) delete-directory)` 重新导出同一
绑定；`4fdb6fa` 起改为自己定义 `npl_unix_delete_directory`。同时导入两个库的
程序在 npli 与 nplc 上都报 `conflicting imported binding`，第一轮探针 04 因此不能
运行；`tools/link-modes.sld` 已用 `only` 绕开。报错也没有给出冲突的名字。

建议恢复重新导出（若是为了去掉对 `(npl process)` 的依赖，则让 `(npl process)`
反过来从共享的内部库取同一绑定）；并在冲突诊断中带上名字和两个来源库。

### R18 typedef 名 struct 的 stub

R10 的修复去掉 stub 中的 POSIX 头，只为 `"struct X"` 形式输出前置声明。
`define-c-struct` 仍接受 `fd_set` 这类 typedef 名：布局探针自带系统头，能通过；
stub 则报 `unknown type name 'fd_set'`。`32cfa51` 的 stub 包含 `<sys/time.h>`，
同一程序可以构建。

建议 stub 中 struct 参数的原型和局部变量一律使用 `void *`：stub 只是转交指针，
不需要完整类型，也就不需要前置声明。`c-stub-struct-declaration`
（`c-stubs.npl`）未被调用，是死代码。

### R19 包缓存屏蔽核心缓存

`c-struct-cache-candidates` 在 `NPL_C_STRUCT_LAYOUTS` 非空时只返回该文件。
外部包按文档指定自己的缓存后，核心的 `timespec`/`tm` 布局找不到，
`(import (npl time))` 回退到调用 cc；`NPL_CC=/usr/bin/false` 下报
`C probe compilation failed for struct timespec`。应改为搜索路径：
先查显式文件（可冒号分隔多个），再查安装/构建位置。

### R20 进程内布局缓存

`c-struct-layout` 先查 `C-STRUCT-LAYOUTS`，键只有 C 类型名。`(npl time)` 已声明
`"struct tm"`（不含 `tm_zone`），用户再以 `tm_zone` 声明同一类型时拿到旧布局，
报 `missing layout for tm_zone`。磁盘缓存有 `c-struct-layout-complete?` 检查，
进程内缓存没有。该缺陷在 `32cfa51` 已存在，第一轮漏审。修法：命中后同样做
完整性检查，不完整则重新探测并合并字段。

### R21 R3 残留

- `time-parts` 只对秒数做 `require-integer`，不限范围；2^70 秒被
  `npl_fixnum_value` 当作 fixnum 解码，mtime 被静默设为 1093195028（npli）或
  1077401276（nplc）。`unix.sld` 注释写了 `time_t` 为有符号 64 位，但只对
  `off_t` 做了检查。
- `open-file` 的 flags 只要求整数：bignum 走进 C 中按符号列表解析的分支，
  报 `car: expected a pair`，且该错误路径泄漏 `path`；未知位被静默忽略。
  NPL 层不接受列表后，C 的列表分支已是死代码。

### R22 杂项

- shebang 只有 npli 接受（`docs/toolchain.md` 已写明）；nplc 对同一文件报
  `bad character byte 33 at line 7 col 1`，文件只有 6 行，行号偏移。若不打算
  让 nplc 接受，至少应修正行号并给出“shebang 仅 npli 支持”的提示。
- `npli-run-file` 的 `read-file` 在 `guard` 之外：`npli DIR` 绕过 `npli-fail`，
  输出 `read-file: short read: "DIR"` 并以 1 退出（正常诊断是 `error: ...`、70）。
- `npl_ffi_struct_pointer` 每次调用都 `npl_string` 分配一个字符串来比较类型名，
  可直接比较 C 字符串。
- `npl_time_mktime_prim`/`_timegm_prim` 以 `errno != 0` 判断 `-1` 是否失败；
  C 标准不保证失败时设置 `errno`，也不禁止成功时设置。macOS 上 -1 秒
  （1969-12-31 23:59:59）往返正确，未在 glibc 上验证；属理论风险。
- `runtime/port.c`（815 行）与 `tools/toolchain.sld`（853 行）本就超过软上限，
  本轮各增 2 行，不单列。

## 建议的测试用例

### R13-R15（`ffi-memory.npl`、`c-structs.npl`、`srfi-170.npl`）

1. 保留 2 万个 `foreign-alloc` 所有者，每个之间做一次小分配，以
   `NPL_GC_NURSERY_BYTES=4096 NPL_GC_VERIFY=1` 运行，全部可写；视图同样。
2. 所有者释放后，经 `define-c-function` 的 `struct:` 参数传入：报可捕获错误。
   以 `pointer+offset` 视图构造短 record 传入：报错。
3. 循环关闭并重新打开目录（含不同路径），对旧句柄 `read-directory`/
   `close-directory` 均报 `directory is closed`，且新句柄不受影响。

### R16-R20（driver、`(tools link-modes)`、`check_full_compiler`）

4. `NPL_NATIVE_LINK=shared` 与 `--native=shared` 产物依赖形态一致；
   `NPL_NATIVE_LINK=dynamic` 报未知模式；`--native=` 覆盖环境变量。
5. `(import (npl process) (npl unix))` 可编译，`delete-directory` 是同一绑定。
6. `define-c-struct` 以 typedef 名声明并作为 `define-c-function` 参数，nplc 可构建。
7. `NPL_C_STRUCT_LAYOUTS` 指向只含外部 struct 的文件，`NPL_CC=/usr/bin/false` 下
   `(npl time)` 仍可导入。
8. 导入 `(npl time)` 后以额外字段声明 `"struct tm"`，npli 与 nplc 都成功。

### R21-R22

9. `set-file-times` 秒数为 2^63、-2^63-1、2^70 报错；`open-file` flags 为 bignum、

10. 带 shebang 的文件：npli 运行；nplc 的诊断行号为 1。
