# 2026-10-29

## C0 GC stack scan reaches the caller of a nested trampoline (fix)

- Decisions (user, 2026-10-27 evening): design-calls D1-D4 accepted as
  recommended; `docs/design-calls.md` status updated. Order: C0, C1a, C1b,
  C1c, then stop for the C2 decision.
- Bug: `npl_trampoline` set the GC stack bottom to its own frame, so a
  collection inside a nested trampoline (`npl_call_sync`, the numeric
  alias slow path) did not scan the frame that called it. Temporaries live
  only in that frame were freed.
- `runtime/trampoline.c`: a trampoline only extends the scanned range
  toward older frames (keeps the current bottom unless none is set or it
  runs below it, as a host may first enter NPL from an older frame). The
  context still records its bottom for the longjmp restore paths. No SSA
  change.
- New test `src/compiler/tests/gc-nested-scan.npl`: 24 fresh strings as
  temporaries of one value-position expression while a bignum `(+ big i)`
  runs through `npl_call_sync`. `tools/check_full_compiler.sh` runs it at
  default settings, nursery 256 B-16 KiB, and once with a 16 KiB nursery
  and `NPL_GC_VERIFY=100`.
- Gate pitfall: the first version ran verify at a 1 KiB nursery with
  `NPL_GC_VERIFY=1`; every collection scans the whole heap twice, and the
  run takes hours (stalled both gates: macOS 22.7 h wall with the host
  asleep, Linux container 8 h+). Measured: 1 KiB with verify every 1000th
  collection 23 s, every 100th > 120 s; 16 KiB every 100th 4 s. Earlier
  "fast" verify timings were wrong: a zsh `env $env` with two assignments
  in one variable passed them as one word, so verify was never set.

Evidence (bash, variables set separately): old runtime (HEAD) vs fixed,
nursery 256 B PASS/PASS, 512 B `vector-ref: expected a vector`/PASS, 1 KiB
`expected a vector`/PASS, 2 KiB `index out of range`/PASS, 4 KiB and
16 KiB PASS/PASS; verify 16 KiB/100 PASS. ASan/UBSan `gc_stress` clean at
4 KiB and 64 KiB nurseries (7,874 and 488 minor collections).
`tools/run_tests.sh` (with relay) all PASS (47, 8.9 min);
`tools/check_linux.sh --skip-current-fixed-point` all PASS (46, 5.2 min).

## C1a continuation parameter without a set! cell (perf)

- `src/compiler/frontend/control.npl` `control-continuation`: a
  single-value continuation rebinds its checked argument with a `let`
  that shadows the parameter, instead of `(set! v (npl_expect_one v))`.
  The parameter is no longer a set! target, so the backend gives it no
  heap cell (`env-bind`). All five continuation sites use this helper.
- fib SSA: the two continuation lambdas lose `npl_cons`, `npl_car`, and
  `npl_set_car`; per fib node 6 -> 4 heap objects, ~21 -> ~13 runtime
  calls.

Self-emit 17.7 -> 15.8 s user (load 21-23, indicative only).
`tools/run_tests.sh` (with relay) all PASS (47, 9.0 min);

## C1b flat closures with inline capture loads (perf)

- `runtime/npl.h`: `NplClosure` gains `capture_count` and `captures[]`
  after the existing fields (offsets of header, function, environment,
  arity unchanged). `runtime/value.c` `npl_make_flat_closure(fn, arity,
  count, captures)`: one allocation; the environment is the closure
  itself, so the trampoline passes it as `%npl_env` and keeps it rooted.
  `npl_make_closure` sets count 0, so runtime callbacks, FFI closures, and
  primitive wrappers are unchanged. `runtime/gc.c` visits the captures.
- `src/compiler/backend/environment.npl`: a lambda is created by one
  `npl_make_flat_closure` call (was `npl_make_environment` +
  `npl_make_closure`); its entry reads capture i with an inline load at
  `%npl_env + 39 + 8i` (was an `npl_environment_ref` call with type and
  bounds checks). No check is needed: only a lambda's own creation site
  builds closures for its function.
- Seed transition in one step (the runtime only gained a function); after
  the relay no generated code or test used `npl_make_environment` or
  `npl_environment_ref`, so both were removed from `runtime/value.c` and

## C1c inline pair and cell access: measured, dropped (no commit of code)

- Tried in `src/compiler/backend/expression.npl`: `car`/`cdr` as a pointer
  and box-tag check plus a field load (runtime call on a miss for the error
  object); cell reads as a load; cell writes inline for a young holder,
  `npl_set_car` for an old one (barrier); `npl_expect_one` as an inline
  `BOX_VALUES` tag check.
- Result: gen2 == gen3, all 35 shared fixtures pass on native, npli, Guile;
  seed 262,127 -> 349,017 lines (+33%); self-emit 9.45 -> 9.52 s user.

  tak 0.99 -> 0.96, vectors 2.81 -> 2.71, callcc 2.76 -> 2.70, loop 0.33,
  closures 1.97 -> 1.99; identical output. No measurable gain: the calls

- Decision (user): drop C1c; `expression.npl` restored, seed unchanged
  (`17a829cf...`). Next O2b, then the C2 design addendum.
  `docs/design-calls.md` records both.

## O2b named-let and letrec loops as jumps (perf)

- `src/compiler/frontend/control.npl`: a `letrec*` binding with a simple
  init (lambda, literal, single-value primitive application) is assigned
  directly instead of through a continuation closure
  (`control-cps-letrec-sequential`; the CPS path moved to
  `control-cps-letrec-init`). The assignment stays in the C function that
  allocates the binding, where the backend can see it.
- `src/compiler/backend/bindings.npl` `self-loop-binding?`: `(set! name
  (lambda ...))` compiles the lambda as a loop when name is a cell of a
  control-converted letrec (placeholder bindings only) allocated in the
  same C function (`LOCAL-LOOP-CELLS`) and this is its only assignment.
  The cell then holds this lambda's closure whenever the lambda runs.
- `environment.npl` `emit-named-lambda` / `emit-lambda-body`: such a lambda
  with fixed, unassigned parameters that captures its name is emitted by
  the shared `emit-self-loop-body` (program.npl, also used by top-level
  functions): the loop label goes after the capture and argument loads.
  `tail.npl` `self-binding?`: the call must see the lambda's captured
  binding of the name (a top-level function: no lexical binding).
  `state.npl`: SELF-FUNCTION gains the entry field; `current-buffer` /
  `set-current-buffer!` so alloc hoisting works in lambda buffers too.
- New shared fixture `tests/r7rs/fixtures/named-loops` (native, npli,
  Guile): plain, nested, and internal-define loops, swap and argument
  order, per-iteration captures, a 3M-iteration loop, reassigned name,
  escaped loop procedure, call from a nested lambda, shadowed name, wrong
  arity, mutual recursion, a loop inside a self-looping function, call/cc
  escape and re-entry, guard, 50,000 allocations. `check_full_compiler.sh`
  checks that four loops jump back to their first label and three must
  not; the same check fails on SSA from the previous seed.

Evidence: gen1 from the edited source; all 35 shared fixtures pass;
gen2 == gen3; installed; strict relay rc=0, gen1 == gen2 == gen3,
`bootstrap/current.ssa` 262,127 -> 264,110 lines, SHA
`6c481477b11260e7789f6ad5ed965479fd1808e3c3e8693d1ab9091a217c88d1`.
Self-emit 9.96 vs 9.87 s user. `tools/run_tests.sh` (with relay) all PASS
(49, 7.9 min); `tools/check_linux.sh --skip-current-fixed-point` all PASS
(48, 4.0 min). Interleaved A/B C1b -> O2b (3 rounds, load 15-19): no
measurable change on any of the 8 workloads (e.g. vectors 2.87 -> 3.03,
lists 5.97 -> 5.84, strings 4.13 -> 4.23, within noise); identical output.

Finding: the bench loops do not jump. Their bodies are `(begin
(vector-set! ...) (loop ...))`, and `control-cps-sequence` converts a
simple first expression by sending it to `(lambda (ignored) rest)`: a
closure and a trampoline bounce per iteration, so the loop call is no
longer in the loop lambda. Probe: `(if (< i n) (inner (+ i 1)) i)` jumps;
the same with `(begin (vector-set! v 0 i) ...)` does not. Next: O2b-2,
sequence conversion keeps a simple first expression in place.
