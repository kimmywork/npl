# Worklog 2026-10-20

## 2026-10-20 11:10 CST — P0 npli cost breakdown (measurement, no repo code change)

Scratch builds under /tmp only (allocation-counting runtime copy, prototype
evaluator variants); host load 15-48, single runs.

- Allocation per loop iteration (instrumented npli, 2000 minus 1000
  iterations): bare loop 1,125 objects / 37 KB; 927 of them come from the
  evaluator's own CPS continuation lambdas (closure + environment + cons),
  most of the rest from string-keyed lookup (`eval-find-binding-owner`,
  `eval-name`, `eval-lookup`). With `(scheme base)` imported: 21,832 objects
  / 726 KB (interpreted `integer.scm`). Import alone: 14.5M objects, 530 MB,
  0.3 s user.
- Prototype A, current evaluator with `+ - = <` bound to native procedures:
  no speedup (bare 20000-iteration loop 0.77 -> 0.84 s user; imported loop
  unchanged, since the import rebinds `+` to interpreted `integer-add`).
  Imported loop is 8x the import-free one (2.92 vs 0.36 s user, 2000
  iterations).
- Raw native primitives are not safe to expose as is: `npl_number_add` on a
  non-number reaches `numeric_error` (runtime/numeric.c, 9 sites), which
  prints and exits 1, so `(guard (e (#t 'caught)) (+ 1 'a))` killed
  prototype A. Native programs avoid it only because `(scheme base)`
  validates first. runtime/ also has many `exit(1)` sites to audit
  (control.c 29, value.c 14, trampoline.c 12, port.c 5, ...).
- Native continuations are fully re-entrant (whole-program CPS): re-entering
  a `call/cc` continuation 4 times and re-entering through native `map`
  both work under nplc.
- Prototype B, a direct-style closure compiler compiled by nplc (s-expression
  subset: quote, if, lambda, calls; lexical addresses; globals as cells):
  evaluator closures are native closures, so native `call/cc` re-entry,
  `map` with escapes, `raise-continuable`, `dynamic-wind` with `raise`, and
  a native primitive error caught by `with-exception-handler` all behave
  correctly. The assumption that native higher-order procedures must stay
  interpreted is false for a closure-compiling evaluator.
- Prototype B speed: 20M-iteration loop 35.7 s user + 25.1 s sys at the
  default 1 GiB threshold (87 s wall), 31.6 s user + 0.7 s sys at 64 MiB
  (177 MB RSS); about 25x faster per iteration than the current npli, about
  40x slower than native (0.83 s). The remaining cost is native non-tail
  calls (heap continuation closure and environment per call, trampoline).
  Not measured: prototype B allocation count (instrumented build failed).

## 2026-10-20 13:40 CST — G1 write barrier and barrier verification (runtime only)

- `runtime/npl.h`: header flags `NPL_FLAG_OLD` (survived a collection, set
  by sweep) and `NPL_FLAG_REMEMBERED`; inline `npl_gc_write_barrier`
  records an old object that receives a young pointer.
- Barriers at the 20 stores into existing objects: value.c 6 (`set-car!`,
  `set-cdr!`, `vector-set!`, record modifier, `append`), control.c 8
  (parameter set, parameterize frames, promise state, wind transition),
  read.c 4 (datum-label patching), string.c 1 (wide-buffer promotion),
  port.c 1 (memory-port growth). The other ~40 pointer stores initialize an
  object allocated in the same function with no allocation in between.
  Checked: every allocated struct starts with `NplHeader`; compiled `storel`

  writes of `NplVal` fields.

  remembered set (emptied at each collection); `npl_gc_verify_barriers`.
  `runtime/gc.c`: `NPL_GC_VERIFY=1` checks before every collection and
  exits 70 on a miss. `npl_string_mark_internal` became
  `npl_string_owned_buffer_internal` for the shared visitor.
