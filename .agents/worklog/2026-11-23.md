## Native package tier decision

- Accepted the two-mode model: core packages are linked by the toolchain
  (A), external packages are loaded at runtime through the FFI (B). Both use
  the same NplVal entry points and binding metadata; the mode is deployment,
  not a source fork.
- Recorded boundary rules: core may use runtime helpers and must not depend
  on external packages; external packages must not link a second runtime and
  should use NPL APIs or caller-owned buffers.
- First migration: move the time wrappers to `lib/npl/time/native/time.c`,
  build `libnpl_time` as a core package, and remove the six primitive rows.

## External package sample recommendation

- Added a sample-package section to the native-package design. First B

## Native package open questions

- Platform: NPL already has `cond-expand`/`features`, but no OS, architecture,
  or target triple. Recorded the proposal: add `darwin`/`linux`,
  `aarch64`/`x86_64`, `64-bit`, a `(npl platform)` library, and a single
  `npl_platform_features` source so `(features)` and `cond-expand` agree.
- GC: B packages stay allocation-free first; caller-provided buffers and
  status returns. Allocation/retention needs a host callback table, never a
  second runtime. Core A may use runtime helpers with normal roots/barriers.
- Errors: B returns status codes; NPL raises with package/symbol context.
  No `npl_primitive_error` from B, no longjmp across FFI.
- Drafted a provisional S-expression `package.meta` with tier, ABI,
  conditional sources/system libraries, bindings, and version fields.
