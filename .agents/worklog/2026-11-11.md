# 2026-11-11

## Compiler adoption step 1: self-compile hot spots (design-data section 5)

Sampling the self-compile (`sample` on the compiler emitting itself) put
the cost in string building, not in the symbol, function, and global
tables the plan named, so step 1 followed the samples.

- `byte-data`/`word-data` (`backend/data.npl`) built a static string's
  ", b 40, b 100, ..." with right-nested `string-append`, copying the rest
  of the text at every character: O(n^2), and the derived syntax source
  (now with `match`) is tens of thousands of characters. Now built by
  halving (`data-units`, runs of 8 characters): same output text.
- After that, the top sample was `identifier-mark-in`: syntax marks were an
  association list searched with `eq?`. `SYNTAX-MARKS` is now an eq hash
  table (`npl_hash_table_ref` with default 0, the old "no mark" value);
  the three resets (`expand-program`, `expand-library-program`, npli
  `make-frontend-session`) make a fresh table with `new-mark-table`. The
  npli session still saves and restores the table object.

Measurements (same host, compiler emitting its own source):

| stage | instructions | user CPU |
|---|---:|---:|
| seed of `d7ff0bd` | 98.20 G | 7.07 s |
| `byte-data` by halving | 27.44 G | 2.47 s |
| syntax marks as eq hash table | 20.29 G | 1.41 s |

Function and global tables (`lk-s`, `backend/state.npl`) did not appear
among the sampled hot spots; they stay association lists until a sample
shows them.
