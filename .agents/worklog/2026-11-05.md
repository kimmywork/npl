# 2026-11-05

## closures: bignum add and multiply in place (perf)

User direction: close the gap to Guile and Racket on lists, closures, and
strings. Profile (`sample`) of closures: 70% `npl_number_mul`, 9%
`integer_add_magnitudes`. The workload's accumulator doubles each
iteration (~2^50000 by the end), so every `(* x 2)` and `(+ x 1)` is a
bignum operation; it is bignum-bound, not closure-bound.

`runtime/numeric.c`:
- `alloc_integer` / `finish_integer`: add and multiply write the result
  limbs into the bignum they return, instead of a calloc'd buffer that
  `box_integer_limbs` copied and freed. Operands stay referenced from a
  volatile local while the result is allocated (a view's limbs point inside
  the operand, which the conservative scan does not count).
- Multiply: rows over the shorter operand (a small multiplier is one pass),
  view fields hoisted into locals, `(* x 1)` and `(* 1 x)` return the other
  operand (the library fold starts at 1).
- Add: the longer operand on the left; after the shorter one, the carry is
  propagated and the rest is copied with `memcpy`.

Bench (CPU s, 3 repeats as in bench.py --scaled; same compiler, old and new
runtime):

| workload | old | new | Guile | Racket |
|---|---:|---:|---:|---:|
| closures | 1.90 | 0.39 | 1.61 | 0.36 |
| fact | 0.46 | 0.44 | 1.05 | 0.65 |
| lists | 4.88 | 4.93 | 1.65 | 0.51 |

(Guile/Racket CPU from the 2026-11-03 bench.py run.) closures and fact
outputs identical; both also pass at a 4 KiB nursery with
`NPL_GC_VERIFY=50` and with no nursery, 64 KiB threshold, `NPL_GC_VERIFY=20`.

## strings: write-string in one port write, string case in C (perf)

Split of the strings workload (20 repeats, CPU s; Guile / Racket): port
writes of `(number->string i)` 1.71 (0.92 / 0.62), `string-upcase` of
100,000 characters 0.84 (0.06 / 0.21), `number->string` alone 0.39
(0.46 / 0.30). `write-string` was a `write-char` loop and resolved the
default port through the `current-output-port` parameter object (a CPS
call); `string-upcase` built a list of every character's mapping and
appended them.

- `lib/scheme/text-io.scm`: `write-string` checks its range as before and
  writes the string (or its `substring`) with one `display`; the default
  ports come from the `current-input-port`/`current-output-port`
  primitives, which read the same parameter objects
  (`runtime/port.c npl_current_output_port`), imported in
  `lib/scheme/base.sld` as `raw-current-*-port`. `write-string` and the
  port helpers are now direct-safe.
- `runtime/unicode.c npl_string_full_case` (row in primitive-table.npl):
  the full case mapping of a whole string, the same tables and simple
  fallback as `npl_char_full_case`/`npl_char_case`. `string-upcase` and
  `string-foldcase` use it; `string-downcase` keeps its Final_Sigma code.

Parts after the change (CPU s): port writes 0.73, write-string of a
literal 0.28 (was 1.27), string-upcase 0.02. Outputs identical, including
non-ASCII write-string ranges and case mappings (checked against Guile;

## lists: send to a literal continuation as a let (perf)

Split of the lists workload (200 x 100,000 elements, CPU s; Guile /
Racket): build 0.41 (0.43 / 0.21), reverse 0.41 (0.34 / 0.26), sum 0.06
(0.10 / 0.20), map 3.85 (0.70 / 0.29). map is the gap: per element two
continuation closures (`npl_make_flat_closure`) and four trampoline
requests. One closure came from control conversion sending a value to a
continuation it had just written as a one-parameter lambda,
`((lambda (v) body) value)`, which the backend makes a closure and calls.

`frontend/control.npl control-send`: when the continuation is a literal
one-parameter lambda, bind the value with a let instead. The single-value
check is in the lambda's body, so it is kept (errors for `(values)` and
`(values 1 2)` in a value context unchanged).

Effect: seed 248,799 -> 213,025 lines (-14%). Interleaved A/B, all
workloads (CPU s, G instructions): lists 5.21 -> 4.87 (-17.1%
instructions), callcc -0.6%, others unchanged in instructions (fib and tak
+8% CPU at 0.12-0.13 s with identical instruction counts: code placement).
map alone 37.5 -> 29.0 G instructions; trampoline requests per element 4 ->
3.

## C3 direct entries for lambdas (perf)

Design: `docs/design-calls.md` addendum C3 (written today on the user's
request, then implemented).

- Runtime: `NplClosure.direct` (code pointer, NULL unless set; not visited
  by the GC), so capture *i* moves to byte 48 + 8i;
  `npl_closure_direct(closure, argc)` returns the entry for a closure with
  that fixed arity, else 0.
- Frontend: `direct-lambda?` runs the C2 walk on a lambda body after the
  top-level verdicts are settled; a direct-safe lambda becomes
  `(219 cps-lambda params direct-body)`. `control-cps-known-call` marks a
  CPS call whose head is a variable that is not a top-level function and
  whose continuation is a literal one-parameter lambda with a small body
  (120 nodes, no lambda) as `(223 head arguments continuation)`.
- Backend: `emit-direct-lambda` emits the CPS lambda, its direct entry
  `$_lambda_N_d(l %npl_env, l %npl_p0, ...)` (captures loaded as in the CPS
  function, stack check with `npl_direct_fallback` to the CPS function),
  and stores the entry into the closure. `emit-closure-call-site` calls the
  entry when `npl_closure_direct` returns one and runs the continuation
  body inline; otherwise the previous CPS call, so errors for wrong arity
  and non-procedures are unchanged.
- Seed transition: the capture offset is in compiled code, so gen1 (built
  by the old seed) is linked with the previous runtime to compile gen2;
  gen2 onward use the new runtime. gen2 == gen3 == gen4.
- Fixture `direct-lambdas` (native, npli, Guile): map/for-each/user map
  over direct lambdas, captured counters, errors and raise under guard,
  bignums, call/cc escape from a mapped lambda, non-procedure, wrong
  arity, primitive and variadic procedures, 1,000,000-deep recursion from a
  direct lambda. `check_full_compiler.sh` checks the `_d` entry and the
  `npl_closure_direct` call in map-one.

Effect: map part of lists (200 x 100,000) 3.5 -> 1.10 s CPU, 29.0 -> 16.8
G instructions (Guile 0.70, Racket 0.29). Seed 213,025 -> 238,627 lines
(+12%: direct entries of lambdas).

## npli: literals are immutable (fix)

Open item: npli let a program mutate literals and quoted data; native
raises "cannot mutate a literal" (static data carries NPL_FLAG_LITERAL).
Measured on both: native rejected string, vector, bytevector, and pair
literals (quoted and self-evaluating); npli accepted all of them.

- `runtime/value.c npl_freeze_literal` (row in primitive-table.npl,
  internal to `(npl primitive)` users): sets NPL_FLAG_LITERAL on a
  value's pairs, strings, vectors, and bytevectors, deeply; stops at an
  already-marked object (datum-label cycles).
- `lib/npl/evaluator-compile.scm eval-literal`: string, vector,
  bytevector, and quote constants are frozen when compiled. String
  constants are copied first (`frontend-datum->runtime` in
  `lib/npl/frontend.sld` copies datum strings with `substring`): the
  text belongs to the frontend's datum.
- Fixture `literal-mutation` (oracle=none: Guile allows the mutation;
  Racket rejects it): quoted strings, vectors, lists, self-evaluating
  literals, vector-fill!/string-fill!, and fresh copies (mutable).

Second open item (numeric errors without imports) was already fixed by the
2026-10-23 evaluator rewrite: npli raises the native error object
(`+: expected an exact integer: a`, `src/repl/tests/primitive-errors.err`);
removed from Open Items. Noted while testing: none.
