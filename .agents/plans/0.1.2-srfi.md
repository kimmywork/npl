# 0.1.2 SRFI Increment Plan

Status: accepted direction, 2026-11-12. This plan follows the
[0.1.0 state review](../reviews/2026-11-12-0.1.0-state-review.md) and keeps
the release line at 0.1.x (patch increments only).

Confirmed on 2026-11-12: canonical `(npl ...)` names with `(srfi N)` aliases;
SRFI-140 as a separate immutable-string library; full SRFI-170 POSIX scope;
include SRFI-146 (Maps) and SRFI-195 (multiple-value boxes) in I3.
No aggregate import syntax or aggregate library: each library is imported
individually. SRFI-18/230 and full SRFI-226 move to 0.1.3.

## Goal

Deliver the requested SRFI libraries in 0.1.2 as a sequence of independently
verifiable increments, with a stable NPL library naming scheme and SRFI
compatibility aliases. Runtime-heavy control and threading work is separated
from the library batch.

## Library naming decision

Canonical implementation libraries live under `(npl ...)`; SRFI numbers are
compatibility aliases. This uses the loader's existing rule that `(npl ...)`
resolves against the standard library root, while `(srfi ...)` already does
the same and `cond-expand (library ...)` detects both by file existence.

Proposed canonical names:

| Area | Canonical library | SRFI alias |
|---|---|---|
| hash tables | `(npl hashtable)` | `(srfi 125)` |
| lists | `(npl list)` | `(srfi 1)` |
| strings | `(npl string)` | `(srfi 13)` |
| string cursors | `(npl string cursor)` | `(srfi 130)` |
| immutable strings | `(npl string immutable)` | `(srfi 140)` |
| vectors | `(npl vector)` | `(srfi 133)` |
| sets | `(npl data set)` | `(srfi 113)` |
| bags | `(npl data bag)` | `(srfi 113)` |
| ranges | `(npl data range)` | `(srfi 196)` |
| streams | `(npl data stream)` | `(srfi 41)` |
| collections | `(npl data collection)` | `(srfi 44)` |
| arrays | `(npl data array)` | `(srfi 47)` |
| boxes | `(npl data box)` | `(srfi 111)` |
| unifiable boxes | `(npl data unifiable-box)` | `(srfi 161)` |
| generators | `(npl data generator)` | `(srfi 158)` |
| bitvectors | `(npl data bitvector)` | `(srfi 178)` |
| maybe / either | `(npl data maybe)`, `(npl data either)` | `(srfi 189)` |
| maps (optional) | `(npl data map)` | `(srfi 146)` |
| multiple-value boxes (optional) | `(npl data multiple-value-box)` | `(srfi 195)` |
| POSIX | `(npl unix)` | `(srfi 170)` |
| time | `(npl time)` | `(srfi 19)` |
| threads | `(npl thread)` | `(srfi 18)` |
| control | `(npl control)` | `(srfi 226)` |

Rules:

- One `define-library` per `.sld`. The canonical `(npl ...)` library owns the
  implementation; the `(srfi N)` library is a thin re-export. Do not duplicate
  procedure bodies.
- Keep library names singular (`(npl list)`, not `(npl lists)`), matching the
  existing `(scheme base)` style and the proposed `(npl data array)` form.
- Do not add top-level `(string)` or `(lists)`. Unknown prefixes currently
  resolve relative to the importing program's directory; reserving them would
  require a loader rule and would collide with user libraries. `(npl ...)` is
  already the extension namespace.
- Keep SRFI-97-style names out of scope unless portability requires them.
  `(srfi N)` is the compatibility spelling used by this project.
- `lib/scheme/libraries.scm` remains the index only for `(scheme ...)` names.
  No index change is needed for `(npl ...)` or `(srfi ...)`.

Document this policy in `docs/extending.md` and the README documentation
section.

### Bulk import syntax

R7RS import sets do not allow grouping inside a library name. A form such as
`(npl data (set range stream))` is not a valid library name, and
`(npl (string list vector time))` is not valid either. The standard forms are
one library name per import, plus `only`, `except`, `prefix`, and `rename`.

Use ordinary imports:

```scheme
(import (npl data set)
        (npl data range)
        (npl data stream))
```

Do not add aggregate libraries or a custom import syntax in 0.1.2. Every
library is imported individually; users can combine ordinary R7RS import
sets with `only`, `except`, `prefix`, and `rename` when needed.

If a macro-style grouping such as `(npl-import (npl data set range stream))`
is wanted later, treat it as a separate frontend language extension: it must
expand to multiple import declarations, needs a seed relay, and is not
R7RS-portable.

## CFFI decision

Do not add generic structs, arrays, or callbacks to the CFFI as part of 0.1.2.
SRFI-170 needs POSIX structs (`stat`, `dirent`, `passwd`, `group`, `utsname`,
`timespec`, `timeval`, `rlimit`, and similar). Implement those as targeted C
wrappers against the existing `NplVal` ABI, returning records, vectors, lists,
or bytevectors.

Rationale:

- Raw struct layout, ownership, array lifetime, and GC pinning are a separate
  design problem; exposing them now would slow the SRFI work and create unsafe
  APIs.
- POSIX wrappers can validate and convert at the C boundary, which is safer
  and easier to test.
- Callbacks into NPL need root registration and a trampoline boundary. Avoid
  them for 0.1.2; add a narrow callback API only if a specific SRFI procedure
  cannot be wrapped safely.
- Revisit a CFFI level C (struct descriptors, array views, callbacks) after
  the SRFI batch, driven by concrete user demand.

## Increments

### I0: plan, naming, and reference docs

- Add this plan, update the workstate, and add a library-naming section to
  `docs/extending.md`.
- Commit the local `docs/reference/srfi-*.html` copies after checking their
  licenses; add a short index if useful.
- Tag the merged 0.1.1 commit and publish its release notes.

Verification: documentation links resolve; no code change.

### I0b: internal namespace (landed)

- Rename `(npl primitive)` to `(npl internal primitive)`.
- Move `(npl frontend)` to `(npl internal frontend)` and `(npl repl-io)` to
  `(npl internal repl-io)`.
- Move the evaluator and eval/load adapter to `(scheme internal evaluator)` and
  `(scheme internal eval-runtime)`. They implement `(scheme eval/load/repl)`
  and depend on `(scheme base)`; keeping them in `(npl internal *)` would make
  the low-level namespace depend on the standard library.
- `(scheme *)` may import only L0/L1 and `(scheme internal *)`; it must not
  import `(npl *)` extensions. The live rules are in `docs/extending.md`.

Status: implemented on `release/0.1.2`; the seed was regenerated after the
primitive-library name change.

### D1: diagnostics and consistency (parallel workstream)

Maps to review F3, F6, F8, and F11.

- Arity errors name the procedure.
- `(2 3)` reports `cannot call a literal`.
- Missing input file returns the same status from `nplc` and `npli`.
- Decide and implement one uncaught-error status and report format.
- Add top-level `file: form N` context to compiler diagnostics.
- Pin the Unicode Character Database version used by `tools/gen_unicode.py`.

Verification: new contracts, `check_driver.sh`, gate, docs.

### D2: source spans and stack traces (after 0.1.2)

Full expression-level source spans require changing the datum representation
and macro expansion; native stack traces require unwinding or shadow-stack
support across direct entries and tail jumps. This is deliberately deferred
until after the 0.1.2 library batch; D1's top-level `file: form N` context is
the interim step.

### I1: foundation libraries

- `(npl list)` / `(srfi 1)`
- `(npl data box)` / `(srfi 111)`
- `(npl data range)` / `(srfi 196)`
- `(npl data maybe)`, `(npl data either)` / `(srfi 189)`

These establish the canonical-plus-alias pattern and a reusable SRFI test
suite. No compiler or runtime change.

Status: implemented on `release/0.1.2`. SRFI 1 uses the MIT reference
implementation, split into three files; SRFI 196 and 189 use the MIT sample
implementations. The `boxes` (6), `srfi-1` (42), `srfi-196` (24), and `srfi-189` (34)
compiler suites pass, and the `srfi-core` fixture passes native, npli, and
the oracle-unavailable lane.

Verification: per-library suites, differential checks with Guile/Racket where
available, gate.

### I2: string libraries

- `(npl string)` / `(srfi 13)`
- `(npl string cursor)` / `(srfi 130)`
- `(npl string immutable)` / `(srfi 140)`

Implement one shared string kernel; build cursors and immutable operations on
top. SRFI-140 is a separate library and does not change `(scheme base)`
constructor semantics. Reuse the existing `NPL_FLAG_LITERAL` immutability
check where possible; add a distinct immutable flag only if the literal flag is
insufficient.

Status: implemented on `feature/srfi-i2-i3` as `(npl string)`,
`(npl string cursor)`, and `(npl string immutable)`. Character-set criteria
(SRFI 14) are not available; criteria are characters or predicates. The
SRFI 13 `string-map` and `string-for-each` names re-export `(scheme base)`
so combined imports stay valid, which drops their optional range arguments.

Verification: `srfi-13` 61, `srfi-130` 29, and `srfi-140` 24 compiler tests;
alias export parity; gate.

### I3: data-structure libraries

- `(npl vector)` / `(srfi 133)`
- `(npl data set)`, `(npl data bag)` / `(srfi 113)`
- `(npl data stream)` / `(srfi 41)`
- `(npl data collection)` / `(srfi 44)`
- `(npl data array)` / `(srfi 47)`
- `(npl data unifiable-box)` / `(srfi 161)`
- `(npl data generator)` / `(srfi 158)`
- `(npl data bitvector)` / `(srfi 178)`
- `(npl data map)` / `(srfi 146)`
- `(npl data multiple-value-box)` / `(srfi 195)`

SRFI-113 uses `(npl hashtable)` (SRFI 125). SRFI-41 uses promises. SRFI-158 uses
closures and `eof-object`. SRFI-44 initially covers lists, vectors, and
strings; do not build a universal dispatch layer without a concrete need.
SRFI-146 uses SRFI-125 or a dedicated persistent-map implementation; decide
after profiling the straightforward hash-table version. SRFI-195 is a small
layer over records or vectors.

Status: `(npl vector)` / 133, `(npl data stream)` / 41,
`(npl data generator)` / 158, `(npl data unifiable-box)` / 161, and
`(npl data multiple-value-box)` / 195, `(npl data array)` / 47,
`(npl comparator)` / 128, `(npl data set)` and `(npl data bag)` / 113, and
`(npl sort)` / 132 and 95 are implemented. SRFI 47 adds `#nA` literals to
the NPL compiler reader and the C runtime reader, so the seed was relayed.
SRFI 44, 146, and 178 remain.

Verification: one suite per library plus cross-library smoke tests, gate.

### I4: time and POSIX

- `(npl time)` / `(srfi 19)`
- `(npl unix)` / `(srfi 170)`

Time: date/time records, conversions, formatting, parsing, and timezone
support through C `clock_gettime`, `localtime_r`, `gmtime_r`, `mktime`, and
`strftime`. Tests pin `TZ`.

POSIX: implement the full SRFI-170 surface, with runtime feature detection
for optional operations and platform guards where POSIX itself makes a
facility optional. Use targeted C wrappers; do not require generic CFFI
structs or callbacks. Return Scheme records, vectors, and lists. Full POSIX
is large enough to split into two or three PRs (file/directory/process,
environment/user/group, terminal/resource/network), but all of it belongs to
the 0.1.2 train.

Verification: timezone-fixed time tests; POSIX tests guarded by platform and
available operations; gate.

### I5: SRFI-226 evaluation

Full SRFI-226 is not part of 0.1.2. Implement only a clearly documented
compatibility subset if it is useful, likely re-exporting existing promises,
exceptions, and parameter facilities. Do not claim SRFI-226 conformance
without prompts, continuation marks, fluids, and threads.

The control workstream needs a design note covering:

- `%call-with-current-continuation`, `%call-in-continuation`,
  `%continuation=?`, and the `%case-lambda-box` primitive;
- prompt tags and continuation barriers;
- continuation marks and their interaction with `dynamic-wind`;
- parameterization/exception-handler stacks as continuation state;
- threads and thread locals, which depend on SRFI-18.

### I6: threads (0.1.3)

- `(npl thread)` / `(srfi 18)`
- `(npl atomic)` / `(srfi 230)`

This is a runtime design increment, not a library increment. It requires
per-thread roots and stack ranges, stop-the-world coordination, per-thread
trampoline/dynamic state, thread-safe allocation and write barriers, and
mutex/condition-variable primitives. It also unlocks SRFI-226 thread
libraries.

## Verification and release

- Each increment is one or more PRs targeting `release/0.1.2`.
- Library-only changes need the gate; no seed relay.
- Runtime or compiler changes need the relay and a test that fails on the
  previous seed.
- Add a `tools/check_srfi.sh` stage or grouped SRFI fixture runner so the gate
  stays readable.
- At the end of 0.1.2: bump `VERSION`, update `CHANGELOG.md`, run macOS and
  Linux gates, tag `v0.1.2`.

## Decision record

No open scope decisions. Individual imports only; SRFI-18/230 and full
SRFI-226 are 0.1.3 work. Any future bulk-import macro is a separate frontend
design.
